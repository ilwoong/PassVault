# 07. 백업과 복구

클라우드 동기화가 없으므로 **백업 파일이 유일한 데이터 보존 수단**이다.
동시에 금고 밖으로 나가는 유일한 데이터이기도 하다 ([01](01-threat-model.md) T-05).

## 설계 전제

| 결정 | 이유 |
|------|------|
| 사용자가 입력한 **백업 비밀번호**로 독립 암호화 | 기기 Keystore에 묶으면 기기 교체·초기화 시 복구 불가 (SEC-04) |
| 마스터 비밀번호 재사용 **허용하되 비권장 경고** | 강제 분리는 사용자가 백업을 안 하게 만든다. 실제 위험(백업 파일 유출 시 금고까지 열림)만 알린다 |
| 복구는 **전량 교체**만 | 병합은 충돌 해결 UI·규칙 스펙이 따로 필요하다. 1차 비범위 |
| JSON 은 플랫폼 내장 `org.json` | 운영 의존성을 늘리지 않는다. JVM 테스트에만 같은 라이브러리를 붙인다 (M8) |
| SAF(`ACTION_CREATE_DOCUMENT` / `ACTION_OPEN_DOCUMENT`) 사용 | 저장소 권한 불필요 (NFR-03). 사용자가 저장 위치를 직접 고른다 |

## BK-01 파일 포맷

확장자 `.pvault`. 파일명 기본값 `passvault-backup-YYYYMMDD-HHmm.pvault`.

```
오프셋  크기   내용
  0      8    매직 "PVAULT\x00\x00" (ASCII 6자 + 0x00 두 개)
  8      1    formatVersion = 1
  9      1    kdfId = 1 (Argon2id)
 10      4    kdfMemoryKiB   (big-endian u32)
 14      4    kdfIterations  (big-endian u32)
 18      4    kdfParallelism (big-endian u32)
 22     16    salt
 38     12    nonce
 50      n    ciphertext = AES-256-GCM(key, gzip(payloadJson), aad = header[0..49])
 50+n   16    GCM 태그 (ciphertext 뒤에 붙는 형태를 사용)
```

- `key = Argon2id(백업 비밀번호, salt, m, t, p, 32)`
- 백업용 KDF 파라미터는 **금고의 캘리브레이션 값을 쓰지 않고 고정값**을 쓴다:
  `m = 64 MiB`, `t = 4`, `p = 2`.
  이유: 복구는 다른(더 느릴 수도 있는) 기기에서 일어나지만, 1회성 작업이라 NFR-01이 적용되지 않는다.
  오프라인 대입에 노출되는 파일이므로 금고보다 강하게 잡는다.
- 헤더 전체가 AAD이므로 파라미터 변조 시 복호화가 실패한다.
- 전체를 메모리에 올린다. 항목 수가 적고(수천 건) 스트리밍 복잡도를 감수할 이유가 없다.
- 상한: 파일 64 MiB, 풀린 평문 64 MiB(압축 폭탄 방지), 헤더의 KDF 메모리 256 MiB. 평문 상한을 더 크게 두면
  버퍼가 두 배로 자라며 상한 검사 전에 메모리가 바닥난다.

## BK-02 payload JSON

```json
{
  "formatVersion": 1,
  "exportedAtEpochMs": 1767225600000,
  "appVersion": "1.0.0",
  "entries": [
    {
      "id": "uuid",
      "type": "LOGIN",
      "title": "...",
      "isFavorite": false,
      "createdAtEpochMs": 0,
      "updatedAtEpochMs": 0,
      "login": {
        "username": "...",
        "password": "...",
        "url": "...",
        "memo": "...",
        "passwordUpdatedAtEpochMs": 0,
        "policy": {
          "minLength": 10, "maxLength": 20,
          "upperRule": "REQUIRED", "lowerRule": "REQUIRED",
          "digitRule": "REQUIRED", "symbolRule": "REQUIRED",
          "allowedSymbols": "!@#$%^&*", "forbiddenSymbols": null,
          "maxRepeatRun": 2, "disallowSpace": true,
          "rotationDays": 90, "rawNote": "..."
        }
      }
    }
  ]
}
```

규칙:
- `type` 에 따라 `login` / `note` / `card` / `identity` 중 **하나만** 존재한다.
- 필드 이름은 [03](03-data-model.md)의 컬럼명과 1:1로 맞춘다.
- **비정규화 캐시(`subtitle`, `last4`, `hasPolicyViolation`, `hasRotationDue`)는 내보내지 않는다.**
  복구 시 재계산한다 (DM-11). 포맷에 중복 진실을 넣지 않는다.
- 설정값·KDF 파라미터·래핑된 키는 내보내지 않는다. 백업은 **항목 데이터만** 담는다.
- JSON 직렬화는 알 수 없는 필드를 무시하도록 설정한다 (상위 버전 파일의 부분 호환).

## BK-03 내보내기 플로우

```
1. [UX-03] 마스터 비밀번호 재인증
2. 백업 비밀번호 2회 입력 (최소 12자)
   - 마스터 비밀번호와 동일하면 "백업 파일이 유출되면 금고도 열립니다" 경고 + 확인
   - 동일 여부는 마스터 비밀번호를 붙잡아 두지 않고, 입력된 백업 비밀번호로 vault_meta 의 VK 를
     풀어 보는 KDF 비교로 판정한다. **이 비교는 LOCK-05 실패 횟수에 넣지 않는다** — 해제 시도가 아니다
3. SAF ACTION_CREATE_DOCUMENT 로 저장 위치 선택 (MIME: application/octet-stream)
4. 항목 전량 조회 → JSON 직렬화 → gzip → Argon2id + AES-GCM → 파일 기록
5. 완료 표시: 항목 수와 파일명
6. zeroize(백업 키, 평문 버퍼)
```

- 평문 JSON을 **임시 파일로 쓰지 않는다** (SEC-01). 메모리에서 바로 암호화한다.
- 실패 시 부분 기록된 파일을 삭제한다.

## BK-04 가져오기(복구) 플로우

```
0. [UX-03] 마스터 비밀번호 재인증 — 전량 교체는 파괴적이다. 해제된 기기를 빌린 사람이
   자기 백업 파일로 금고를 통째로 덮어쓰는 경로를 막는다 (M8 에서 추가). 잠금 화면의 복구 경로는
   BK-05 의 수용 한계 참조
1. SAF ACTION_OPEN_DOCUMENT 로 파일 선택 (64 MiB 를 넘으면 거부)
2. 매직·formatVersion 확인 → 지원하지 않는 버전이면 중단 (BK-07)
3. 백업 비밀번호 입력 → Argon2id → AES-GCM 복호화 (태그 실패 = 비밀번호 오류 또는 파일 손상)
4. JSON 파싱 + 검증 (BK-08)
5. 사용자에게 **요약 확인**: "항목 N건. 현재 금고의 모든 항목이 삭제되고 교체됩니다." → 확인 필수
6. 단일 트랜잭션: 전체 DELETE → INSERT. 캐시 컬럼 재계산
7. 완료 후 목록으로. 실패 시 트랜잭션 롤백 — 기존 데이터는 그대로 남는다
```

## BK-05 금고를 열 수 없을 때의 복구

마스터 비밀번호를 잊었거나 DB가 손상된 경우. unlock 화면의 "백업 파일에서 복구" 진입점 ([UX-02](05-ui-flows.md)).

```
1. 백업 파일 선택 + 백업 비밀번호로 복호화 검증 (여기까지 성공해야 다음으로 간다)
2. **새 마스터 비밀번호 설정** (CRY-10과 동일: 새 salt, 새 VK, 새 DB)
3. 기존 vault_meta 와 DB 파일을 삭제하고 새로 생성
4. 복호화해 둔 항목을 새 DB에 기록
```

- 2번이 성공한 뒤에만 3번을 실행한다. **순서를 바꾸면 복구 실패 시 데이터가 전부 사라진다.**
- 이 플로우는 "기존 금고 폐기"가 명시적으로 표시되고 확인받아야 한다.
- 손상(`CORRUPT`) 화면에서도 같은 진입점을 둔다 (ARC-06).
- 구현: 금고 생성의 `Absent` 전용 가드(CRY-10)에 대한 **유일한 예외**다. 복호화 성공 뒤에만 부를 수 있는
  별도 경로(`recreateVault`)로 둔다. 새 메타를 원자적으로 쓰고, 기존 DB 파일을 지우고, 새 DB 를 열어
  항목을 기록한 **뒤에** 세션을 `UNLOCKED` 로 바꾼다 — 상태가 먼저 바뀌면 화면 분기가 바뀌어 기록 작업이
  취소될 수 있다. 그 사이 화면이 꺼지거나 앱을 떠났으면 기록을 마친 뒤 `UNLOCKED` 대신 `LOCKED` 로 끝난다
  ([LOCK-03](06-lock-policy.md)). 사용자는 새 마스터 비밀번호로 해제한다.
- 백업 파일 없이 금고를 되살리는 경로는 **존재하지 않는다.** 백도어를 만들지 않는다 (NFR-05).
- **수용하는 한계**: 이 경로는 인증 없이 기존 금고를 폐기한다. 비밀번호를 잊은 사용자의 출구라 인증을 요구할 수 없다.
  BK-04 의 재인증은 *해제된* 금고에서의 덮어쓰기만 막는다 — 기기를 쥔 사람이 금고를 잠그고 이 경로로 덮어쓰는 것은
  막지 못한다. 잃는 것은 가용성이지 기밀성이 아니고(기존 비밀은 드러나지 않는다), 되돌리는 수단은 사용자의 백업 파일이다.

## BK-06 오류 구분

사용자가 다음 행동을 결정할 수 있을 만큼만 구분한다.

| 상황 | 메시지 방향 |
|------|-------------|
| 매직 불일치 | "PassVault 백업 파일이 아닙니다" |
| `formatVersion` 이 더 높음 | "최신 버전 앱에서 만든 파일입니다. 앱을 업데이트하세요" |
| GCM 태그 실패 | "백업 비밀번호가 올바르지 않거나 파일이 손상되었습니다" — 둘을 구분할 방법이 없으므로 합쳐서 표시한다 |
| JSON 파싱·검증 실패 | "파일이 손상되었습니다" |
| 파일 I/O 실패 | "파일을 읽을 수 없습니다" |

## BK-07 버전 호환

- 읽기: `formatVersion <= 현재` 만 받는다. 상위 버전은 거부한다 (부분 복구가 더 위험하다).
- 쓰기: 항상 현재 버전으로 쓴다. 하위 버전 내보내기는 지원하지 않는다.
- 포맷 변경 시 이전 버전 파일을 읽는 테스트를 **고정 픽스처 파일로** 저장소에 커밋한다 ([TST-09](08-testing.md)).

## BK-08 가져오기 검증 규칙

손상·악의적 파일에서 앱이 깨지지 않아야 한다.

- `id` 가 UUID 형식이 아니거나 중복이면 거부.
- `type` 이 알 수 없는 값이면 거부 (해당 항목만 건너뛰지 않는다 — 조용한 데이터 손실 방지).
- `title` 이 비어 있으면 `"(제목 없음)"` 으로 대체.
- 문자열 길이 상한을 둔다 (제목 200자, 그 밖의 모든 문자열 20,000자). 초과 시 거부.
  편집 화면이 같은 상한을 입력 단계에서 강제한다 ([UX-06](05-ui-flows.md)) — 그래야 내보낸 파일이 항상 이 검증을 통과한다.
- 항목 수 상한 50,000건. 초과 시 거부.
- 날짜·숫자 필드가 범위를 벗어나면 null 로 처리.
- `entries` 가 빈 배열인 것은 **유효하다** (빈 금고 백업).
